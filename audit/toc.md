### A receipt for a downward rounding omits the rounding line and the grand total

- **Slug:** `receipt-drops-negative-rounding`
- **Severity:** high
- **Category:** correctness
- **Status:** fixed
- **Report:** [iterations/002/report-03-receipt-drops-negative-rounding.md](./iterations/002/report-03-receipt-drops-negative-rounding.md)
- **Files:** `src/lib/receipt/build-summary.ts`, `src/lib/receipt/create-receipt-data.ts`, `src/pages/Pos/Draft/z-Methods.tsx`, `src/services/transaction/live.ts`, `src/pages/Record/Item/z-Receipt/z-Summary.tsx`

`build-summary.ts` only prints the "Pembulatan" and "Total Semua" lines when `record.rounding > 0`, so a sale rounded *down* (a reachable, tested path: the Pembulatan cell has `allowNegative`, `submit` has a "supports negative rounding" unit test) prints a receipt showing `Total Rp100.500` and `Pembayaran Rp100.000` with no line explaining the Rp500 and no grand total. The dead `record.rounding > 0 ? "" : "-"` inside that block shows the guard was meant to be `!== 0`. Nothing in `src/lib/receipt/` tests the summary builder, which is why it survived.

### Catalogue cache decides "unchanged" from wall-clock milliseconds, so a write can be silently dropped

- **Slug:** `catalogue-invalidation-by-wall-clock`
- **Severity:** high
- **Category:** correctness
- **Status:** fixed
- **Report:** [iterations/002/report-01-catalogue-invalidation-by-wall-clock.md](./iterations/002/report-01-catalogue-invalidation-by-wall-clock.md)
- **Files:** `src/services/product/live.ts`, `src/services/listing/live.test.ts`, `src/services/product/stock-sql.ts`, `src/services/listing/live.ts`

`ProductService.hydrate()` reuses the previous `ProductState` when every `*_updated_at` number matches, and those numbers are `Date.now()` stamped by the writer. Two writes to the same row inside one millisecond therefore read back as "unchanged": the ref keeps the old object, emits nothing, and the POS keeps the old price and old stock. This is exactly the stale-catalogue class iteration 1 fixed, re-introduced by its own optimisation — and it is why `bun test` (the CI gate that now blocks the MSI build) fails on `listing service > repricing a listing is visible without a reload` when the whole suite runs, yet passes when the file is run alone.

### POS search re-queries the whole catalogue on every keystroke, unlike every other search box

- **Slug:** `pos-search-unthrottled`
- **Severity:** medium
- **Category:** performance
- **Status:** partial
- **Report:** [iterations/002/report-06-pos-search-unthrottled.md](./iterations/002/report-06-pos-search-unthrottled.md)
- **Files:** `src/pages/Pos/Draft/z-Listing.tsx`, `src/pages/Restock/Draft/z-Listing.tsx`, `src/services/listing/live.ts`, `src/lib/search/listings.ts`, `src/pages/Pos/page.tsx`, `src/pages/Pos/Draft/z-ListingCard.tsx`, `src/pages/Product/z-Search.tsx`

The POS search bar is the only search in the app that is not debounced: Product, Extra and Record all use `useDebouncedCallback`, while `Pos/Draft/z-Listing.tsx` feeds every keystroke straight into `listing.get.search`, which rebuilds a catalogue-sized `Map` and rescoring/ sorting pass per character. The same screen also rebuilds a catalogue-wide code map (`findLineIssues`) on every cart edit, and `ListingCard` is unmemoised with inline callbacks, so one keystroke re-renders every `useSortable`/`motion` card. Small catalogues hide it; a grosir catalogue turns typing into a stutter.

### Printer IPC commands run on the main thread and freeze the POS while spooling

- **Slug:** `print-commands-block-main-thread`
- **Severity:** medium
- **Category:** tauri
- **Status:** fixed
- **Report:** [iterations/002/report-05-print-commands-block-main-thread.md](./iterations/002/report-05-print-commands-block-main-thread.md)
- **Files:** `src-tauri/src/printer.rs`, `src-tauri/src/auth.rs`, `src-tauri/src/lib.rs`, `src/lib/printer.ts`

`get_printers` and `print_pdf` are synchronous `#[tauri::command]` functions (`src-tauri/src/printer.rs:66-77`), so on Tauri v2 they run on the main thread: Win32 printer enumeration, temp-file write and `WinPdfPrinter::print` all block the webview event loop. Printing happens immediately after Bayar, so a slow or offline printer freezes the whole POS window right when the cashier needs to start the next sale. `auth.rs` already moved its blocking work to `spawn_blocking` with a comment explaining exactly this hazard; `printer.rs` was left behind.

### The dashboard's "today" is frozen at mount, so a shop PC open past midnight reports yesterday as today

- **Slug:** `dashboard-day-frozen-at-mount`
- **Severity:** low
- **Category:** correctness
- **Status:** fixed
- **Report:** [iterations/002/report-08-dashboard-day-frozen-at-mount.md](./iterations/002/report-08-dashboard-day-frozen-at-mount.md)
- **Files:** `src/pages/Home/use-stats.ts`, `src/pages/Home/z-IncomeCard.tsx`, `src/pages/Money/use-range.tsx`, `src/pages/Record/use-records.ts`, `src/pages/Record/use-time.ts`

The Beranda dashboard derives "today" once, inside `useMemo(dayRanges, [])`, and queries on `[range.today.start]` with no record-revision dep — so an app left open across local midnight keeps showing yesterday's figures as "Pendapatan Hari Ini", and nothing short of a route remount refreshes it. `Money/use-range.tsx` freezes its default month window the same way. Every other day-scoped screen (`Record/use-records.ts`, `Debt/use-data.ts`) already subscribes to `record.get.revision`; the dashboard is the one that does not.
